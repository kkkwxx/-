## 1. 选型判据

### 1.1 五条判据（按优先级）

| # | 判据 | 含义 | 反例 |
|---|---|---|---|
| 1 | **成熟度** | 有 ≥2 年持续维护、有稳定 major 版本、文档可查、有真实生产使用 | 单人 toy 项目、连 README 都没有 |
| 2 | **许可证可用** | MIT / Apache-2.0 / BSD 优先；AGPL 只允许"不进仓库、不作为交付物一部分"的用法 | 把 AGPL 服务打包进交付物并把仓库设为私有 |
| 3 | **形态成本** | **库 > 内嵌进程 > 独立常驻服务**，同等能力取更左 | 为了 18 个 RSS 源再起一套 Node 服务 |
| 4 | **一周可交付** | 引入后半天内能产出第一行可用代码 | 需要先学 DSL、先搭集群、先配模型权重 |
| 5 | **不重复能力** | 同一能力只保留一个实现 | 同时装 feedparser + Miniflux + Scrapy 三套解析 |

### 1.2 本轮红线

一周工期下，"复用"最大的风险不是"复用不够"，而是**复用失控**——每加一个组件都合理，加起来就录不完视频。因此 v2.0 给自己定了硬上限：

| 红线 | 上限 | 实际用量 |
|---|---|---|
| 新增库级组件 | ≤ 3 | 3（Pro Components、openapi-typescript、Faker）——**已满** |
| 新增常驻服务 | 0 | 0 |
| 新增基础设施 | 0 | 0（例外：`pgvector/pgvector:pg16` 同 major 换 tag） |

**红线一旦触顶，后续任何"再加一个吧"都必须先删掉一个。** 这条规则的作用不是限制能力，而是保护一周工期。

## 3. 逐项评估

### 3.1 RSSHub —— 不部署（但记录为将来选项）

**它解决什么问题**：给没有 RSS 的站点生成 RSS 路由，社区已贡献大量站点的现成路由。

**为什么本项目不需要**：

1. 需求文档列出的信源（NASA / ESA / Fermilab / ATel / ScienceDaily / phys.org / Watchers / 天聚数行 / Google News）**全部本来就提供 RSS 或 API**。
2. 实测失败的 3 个源，失败原因是**网络与鉴权**，不是"缺 RSS 入口"：
   - `esa_news`：连接被中断，备用地址 25 s 超时
   - `atel`：403，需要 token
   - `tianapi_science`：404 需要 key
   RSSHub 对这三种情况**一个都解决不了**。
3. 代价：一个 Node 常驻服务（违反红线 2）+ AGPL-3.0 的网络服务条款。

**保留的用法**：如果将来要接微博、豆瓣、短视频这类 C 级线索源，公共 RSSHub 实例是成本最低的路径——但那是"待定池线索采集"，不是 MVP 范围，且届时**只作为外部服务调用，不把代码纳入交付物**。

### 3.2 Miniflux —— 不引入

**它解决什么问题**：多用户 RSS 阅读器，自动更新、全文获取、全文搜索、REST API、OPML。

**为什么不需要**：我们不是"读 RSS"，而是"把 RSS 变成业务数据"。Miniflux 的文章模型面向阅读器（已读/未读/星标/分类），而我们需要 `source_level`、`event_type`、`is_event`、`fact_anchor`、`review_status`——这些它一个都没有，最后还是要在它旁边再建一套业务库，等于两套数据源。

**能力对照**：它提供的"解析 RSS / 自动更新 / 全文获取"，feedparser + APScheduler + Trafilatura 三件套在 100 行内就能覆盖，而且**不新增服务**。

**结论**：能力重叠 + 形态成本过高，直接排除。

### 3.3 Crawl4AI —— 降级为后置（本轮最重要的"拒绝"）

这是另一个 agent 重点推荐的方案，我认可它的能力，但**一周工期下它的收益小于风险**：

| 维度 | 评估 |
|---|---|
| 能力 | 浏览器渲染 + 正文提取 + Markdown 转换 + Schema 结构化，确实覆盖我们的正文需求 |
| 依赖 | 基于 Playwright/Chromium，约 200 MB 浏览器；与 v1.0 已定的"不引 Playwright"直接冲突 |
| 收益 | 我们的正文用途是给 LLM 抽事实锚点，不需要"完美 Markdown" |
| 实测替代 | Trafilatura 在 10 条真实新闻上成功率 **80%**，成功的 8 条平均 4,347 字，抽取耗时 53 ms |
| 失败原因 | 唯一的 2 条失败是 phys.org 返回 **403**（站点策略），**换浏览器也大概率被拦** |
| 演示风险 | 录制视频前必须预下载 Chromium 并离线验证；机器换一台就重来一遍 |

**决策**：不进 v2.0。触发条件写清楚——**当 Trafilatura 的正文成功率（排除 403 类站点策略）低于 80%，或出现"内容必须 JS 渲染才能拿到"的目标源**，再单独评估；届时按"库级引入（`pip install crawl4ai`）+ 预下载浏览器"的方式加，不引入独立服务。

### 3.4 Firecrawl —— 不引入

能力与 Crawl4AI 高度重合（Scrape / Crawl / Extract / Markdown），但自托管需要 Redis + PostgreSQL + 浏览器服务，主体 AGPL-3.0。**同时引入 Crawl4AI 与 Firecrawl 是明确的反模式**（能力重复，违反判据 5）；本项目两个都不选。

### 3.5 Scrapy —— 不引入（但要说清区别）

Scrapy 是"爬虫开发框架"，不是"成品采集规则库"。它帮我们解决请求调度、并发、去重、中间件、Pipeline——**这些恰恰是我们在 `01-总体架构.md` 里已经用 APScheduler + `task_run` 表定义清楚的部分**。

两套调度器的直接后果是"任务状态有两个真相"：Scrapy 内部有它的 dupefilter 与 retry 状态，我们的 `task_run` 也有，Dashboard 上就说不清一条源到底成功没成功。这与架构里"`task_run` 是唯一任务真相"的设计冲突。

**如果真有 HTML 列表页源**：写一个 80 行的 httpx + BeautifulSoup 适配器，复用现有 `task_run`，比引入 Scrapy 快得多。

### 3.6 Trafilatura —— 采纳并升为唯一主方案

- **Apache-2.0**（1.8.0 起），库级，无浏览器依赖。
- **已实测**：Windows + Python 3.12.16 有 lxml 6.1.3 现成轮子，`uv add` 无需编译；成功样本抽取 3—103 ms。
- **为什么不用"Trafilatura + Crawl4AI 双通道"**：双通道意味着每条新闻要判断"该用哪个"，判断逻辑本身就是 bug 源。单通道 + 明确回退链（`ok` / `blocked` / `thin` / `skipped`，见 `技术栈.md` §5.6）更可控。

### 3.7 LiteLLM —— 不引入

价值在于统一多家模型供应商的调用方式。本项目只有一个端点（百炼 OpenAI 兼容），换供应商的实际工作量是**改 `base_url` 和 model 名**，加一层网关只增加一层抽象和一份依赖。另一个 agent 自己也写了"不是必需品"，这里采纳这个判断。

### 3.8 Promptfoo —— 从"高优先级"降为"可选加分项"

**我认可它的核心洞察**：需求文档里的验收条件是天然断言（标题 10—18 字、3—5 个候选、导语 20—60 字、摘要 80—120 字、灵异类必须标娱乐属性、不得绝对化）。把这些变成测试用例，比反复调 prompt 更有价值。

**但把它作为交付物的主路径有三个问题**：

1. 它自身迭代很快，配置 schema 常变，一周内写的配置下周可能就要改；
2. 它是 Node 生态的**开发期**工具，与运行时无关——引入它不提升交付物质量，只提升"展示效果"；
3. 同一件事 pytest 参数化能做，且**能进 CI、能用 `uv run pytest` 一条命令复现、能随仓库一起交付**。

**决策**：主路径 = `fixtures/eval/labeled.jsonl` + `tests/eval/` 参数化 + JSON 指标报告；promptfoo 用 `npx` 临时跑同一份用例做交叉验证，**不进依赖、不进仓库**。

### 3.9 RapidFuzz —— 采纳（v1.0 已有）

MIT、C++ 内核的 Python 库，标题相似度计算比 difflib / fuzzywuzzy 快一到两个数量级。用于即时去重的"标题指纹"和事件级去重的候选召回。**已在本项目栈内，无需变更。**

### 3.10 Datasketch —— 后置

MinHash / LSH，适合大规模近重复检测。MVP 的数据量是"每天几十到几百条"，PostgreSQL `pg_trgm` + rapidfuzz 完全够；等出现"正文级近重复"真实需求再引入。**后置不等于永远不用**，触发条件：出现同一事件被多家媒体改写、标题差异大但正文高度相似，且人工合并成本明显时。

### 3.11 @ant-design/pro-components —— 采纳（本轮最大收益）

**为什么这是"复用红利"**：一周工期里前端工作量的分布是极不均匀的——审核工作台、信源管理、Dashboard 三者占掉大部分时间，而它们的本质都是"带搜索的表格 + 详情面板 + 编辑表单"。

| 手写 AntD 5 | Pro Components |
|---|---|
| `<Table>` + 手写搜索栏 + 手写分页状态 + 手写列显隐 + 手写批量选择（约 150—200 行/页面） | `<ProTable>` 一份 `columns` 配置全部得到 |
| `<Drawer>` + `<Descriptions>` + 手写字段映射 | `<ProDescriptions>` 直接吃数据对象 |
| `<Form>` + 手写校验逻辑 | `<ProForm>` + `rules`（标题 10—18 字直接声明） |

**风险与已验证事实**：唯一的风险是与 antd 5 的 peer 版本冲突。**已实测**：`@ant-design/pro-components@2.8.10` + `antd@5.29.3` + `react@18.3.1` 无冲突，真实审核台页面 `tsc -b && vite build` 通过。

**代价**：打包体积。实测单 chunk 1,835 kB（gzip 568 kB），触发 Vite 警告 → 已在 `技术栈.md` §5.4 写入"路由级懒加载"作为配套要求。

### 3.12 openapi-typescript —— 采纳（成本最低的质量提升）

FastAPI 天生输出 `/openapi.json`，把它转成 TS 类型只需一条命令。**已实测**：

- 生成到 `schema.d.ts`，中文 `Literal` 枚举（`深空/粒子`、`异常灵能`）完整保留；
- 负向验证：`source_level: 'D'` 与 `event_type: '体育'` 都被 `tsc` 精确拦截，错误信息直接列出合法枚举。

这把"后端改字段、前端悄悄过期、演示当天白屏"这条最典型的翻车链，变成**编译期错误**。成本是一条 npm script，收益是整个前后端契约。

### 3.13 pgvector/pgvector:pg16 —— 采纳（换 tag，不换架构）

**它不是什么**：不是"引入向量数据库"。它是**同一个 PostgreSQL 16 major 的镜像**，只多了 `vector` 扩展。实测 `select version()` 为 16.16，`pg_trgm` 1.6 与 `vector` 0.8.7 均可 `CREATE EXTENSION`。

**为什么值得换**：架构明确说"向量语义去重初期不做，不够再引 embedding"。如果那时主库是 `postgres:16-alpine`，就要么换镜像、要么加独立向量库；换成 pgvector 镜像后，**将来只差一次 `CREATE EXTENSION` 和一个 `vector(768)` 列**。

**风险**：镜像拉取失败（实测成功，digest `sha256:484e8380...`）。回退路径明确：改回 `postgres:16-alpine`，MVP 用到的 `pg_trgm` 是 PG 官方 contrib，两个镜像都有，**功能零损失**。

### 3.14 full-stack-fastapi-template —— 参考，不 fork

FastAPI 官方组织的全栈模板（MIT），有成熟的 JWT 登录、Alembic 初始化、pytest fixture 结构、Docker Compose 组织方式。

**为什么只参考不 fork**：它带了完整的多用户/多租户/邮件/CI 结构，我们只需要单管理员；fork 之后要裁剪掉一半，裁剪成本大于重写成本，还会引入不熟悉的代码。

**借什么**（明确清单）：

- JWT + `HttpOnly` Cookie 的登录实现细节（`技术栈.md` §5.2 已定）
- Alembic `env.py` 的初始化与 autogenerate 配置顺序
- pytest 里"测试库 + 事务回滚"的 fixture 写法

### 3.15 Faker —— 采纳（dev 依赖）

一周工期里"造演示数据"被严重低估：要覆盖 10 条验收用例（中微子/科普/小行星/星空图/类地行星/脑电/头环广告/道士综艺/星座运势/UFO 视频），还要有正常量级的列表数据让 ProTable 分页看起来真实。手写这些 JSON 是纯体力活且容易前后不一致。

Faker 生成人名、机构名、时间、URL 片段，配合固定的业务模板，能批量产出 seed 数据与边界样例。**只在 dev 依赖里，不进运行时。**

### 3.16 SQLAdmin —— 后置

只读数据巡检的价值有限：Dashboard 已经覆盖"采集量/失败率/待审核"，真要查数据可以直接 `psql` 或 `/docs`。等出现"运营需要自己查表但不能碰代码"的真实需求再说。

### 3.17 refine.dev —— 不引入

它的定位是"用资源声明生成 CRUD 后台"，前提是业务能用 `resource + list/create/edit/show` 四件套描述。

我们的核心流程恰恰不是 CRUD：`pending`（待定）→ 补充证据 → 重新校验 → `candidate` → 人工通过 → `published`，中间还夹着"同事件的其他来源"和"审核日志前后值对照"。把这些硬塞进 refine 的资源模型，要么放弃它的自动化（那引入就没意义），要么改造业务去迁就框架（这是本末倒置）。

**结论**：AntD 5 + Pro Components 的"组件级复用"比 refine 的"框架级复用"更契合本项目——组件可以随便拼，框架要求你按它的世界观建模。

### 3.18 Celery + Redis —— 拒绝

`01-总体架构.md` §7-6 已定：APScheduler + `task_run` 表，Worker 独立进程。

理由在 v2.0 里更充分：Celery + Redis 是**两个常驻服务**，直接违反红线；而我们的任务规模是"18 个源、15—120 分钟一轮、单机单 Worker"，`task_run` 表能提供 Celery 给不了的东西——**任务状态和业务数据在同一个事务里**，`task_run.status` 与 `raw_item` 落库可以原子提交。人工重跑也只是一条 `INSERT`。

### 3.19 向量数据库 / sentence-transformers —— 拒绝

架构已定"初期不做 embedding 语义去重"。引入向量库要新增一个服务（违反红线），引入 sentence-transformers 要下载模型权重（几百 MB 起）。而 `pg_trgm` 已经能用 `similarity()` 做标题级相似度，覆盖 MVP 去重的大头。

**预留而非预埋**：pgvector 镜像把我们"将来能加"的成本从"换镜像 + 迁数据"降到"`CREATE EXTENSION` + 加一列"，这就够了。

## 5. 复用边界：哪些必须自己写

这是本文最重要的一节——**"复用"的边界划在哪里，决定了这个作品是不是"自己的"**。

| 必须自己写（业务差异化，复用不到） | 为什么复用不到 |
|---|---|
| **信源 A/B/C 分级与域名定级规则** | 需求定义的等级与"Google News 命中要回溯媒体域名再定级"是本题特有逻辑 |
| **四类内容判定 + `is_event` 标准** | "中微子实验成果 vs 中微子科普"的区别只有业务方说得清 |
| **跨来源事件去重策略** | 实体 + 动作 + 时间 → `event_cluster`，是本题的领域模型 |
| **事实锚点提取与"标题必须先有事实"的顺序约束** | 通用框架默认"先写内容再校验"，我们要反过来 |
| **标题 10—18 字 / 导语 20—60 字 / 摘要 80—120 字 / 风险 flag** | 需求逐字规定的口径，包括"字数是否含标点"这类细节 |
| **审核状态流转（候选 / 待定 / 通过 / 拒绝 / 已推送）与补证流程** | 这是本题的产品核心，通用审核平台表达不了 |
| **业务数据模型（`article` / `event_cluster` / `published_article` 快照）** | 发布快照 + 只读栏目是本题的设计决策 |
| **演示双轨（真实采集 + 回放）与评测集** | 交付物特有需求 |

反过来，下面这些**一律复用，不自己写**：RSS 解析、HTTP 抓取与重试、正文抽取、定时调度、模型调用、表格/表单/图表组件、ORM 与迁移、模糊匹配算法。

**一句话原则**：**"通用能力一行都不写，业务判断一句都不省。"**

## 6. 参考实现清单（借什么、不借什么）

"参考"和"复用"是两件不同的事：参考只借结构与经验，不引入依赖、不复制代码。本轮参考了三个来源，借的东西逐一写死，避免"说不清哪里是自己的"。

### 6.1 借 `fastapi/full-stack-fastapi-template`（MIT）

| 借 | 不借 |
|---|---|
| Alembic `env.py` 的初始化顺序（先建 `Base.metadata`，再 `target_metadata`，最后 autogenerate） | 多用户 / 多租户 / 权限模型 |
| pytest 的"测试库 + 每用例事务回滚"fixture 结构 | 邮件服务、注册流程、密码找回 |
| JWT 放 `HttpOnly` Cookie 的实现细节 | 其 CI / pre-commit / Docker 编排 |
| `backend/app/core/config.py` 的分层配置思路 | 其目录层级（我们按 `api/models/schemas/services/tasks` 组织） |

### 6.2 借 `feedparser` 官方文档（未引入新依赖）

| 借 | 不借 |
|---|---|
| `bozo` / `bozo_exception` 的判定用法（用来区分 `not_a_feed` 与 `empty_feed`） | 其内部 `sgmllib` 兼容层细节 |
| `published_parsed` → `datetime` 的转换写法 | 自定义解析器 |
| `entry.source` 取 Google News 媒体域名的用法（已实测 44/44 可取） | — |

### 6.3 借 Trafilatura 官方文档的推荐参数

`favor_precision=True`、`include_comments=False`、`include_tables=False`——这三个参数组合已在实测中确认能在新闻页拿到干净正文。**不借**它的 `fetch_url` / 批量下载功能，抓取仍由我们自己的 httpx + tenacity 负责（这样才能统一重试、UA、超时和 `task_run` 记录）。

### 6.4 明确不参考的东西

- **不做"通用新闻处理框架"调研**：需求里的"中微子成果收录 / 中微子科普拒绝 / 道综艺待定"是业务规则，任何通用框架都表达不了。
- **不做"通用审核平台"调研**：同上，状态机是本题产品核心。
- **不参考第三方爬虫的"反爬绕过"技巧**：ATel 需要 token、phys.org 返回 403，正确做法是尊重站点策略并走降级（回退 RSS 摘要），而不是伪装 UA 硬闯。

## 7. 与 v1.0 的差异、影响面与回退路径

### 7.1 差异清单

| # | 项 | v1.0 | v2.0 | 影响面 |
|---|---|---|---|---|
| 1 | 前端表格/表单 | AntD 5 手写 | + `@ant-design/pro-components` 2.x | 审核台、信源管理、Dashboard 页面写法；需配路由级懒加载 |
| 2 | 前后端类型 | 手写 TS interface | `openapi-typescript` 从 `/openapi.json` 生成 | 新增 `npm run gen:api`；`schema.d.ts` 进仓库 |
| 3 | 演示数据 | 手写 fixture | + `Faker`（dev） | seed 脚本与边界样例 |
| 4 | 数据库镜像 | `postgres:16-alpine` | `pgvector/pgvector:pg16` | 仅 `docker-compose.yml` 一行；不启用 vector 类型 |
| 5 | 后台检索 | `ILIKE` | `pg_trgm` GIN + `tsvector` | 迁移里加 `CREATE EXTENSION` 与索引 |
| 6 | 拒绝清单 | 16 项 | 22 项，每项带替代 | 无代码影响，纯决策记录 |
| 7 | 采集 HTTP | 未规定 | **§5.5 单 Client + tenacity 重试 + 并发 4** | collector 必须按此实现，否则实测约 40—60% 首连失败 |
| 8 | 正文抽取 | Trafilatura | Trafilatura + **回退链** `ok/blocked/thin/skipped` | extractor 新增状态字段与降级分支 |
| 9 | 验收口径 | 7 条 | 11 条（新增零常驻服务、文档一致、类型链、采集韧性） | 交付前逐条自检 |

### 7.2 不变的部分（重要）

- **总体架构完全未动**：`01-总体架构.md` 的主链路、状态机、模块边界、数据实体、部署图（§4）一个字都没改。
- **没有新增常驻服务**：`docker compose ps` 仍然只有 `db`。
- **没有新增中间件**：仍然没有 Redis / Kafka / ES / Nginx。
- **同步 SQLAlchemy + APScheduler + `task_run` 的决策不变。**

### 7.3 回退路径（逐项）

| 项 | 触发条件 | 回退动作 | 残余成本 |
|---|---|---|---|
| Pro Components | peer 冲突或构建失败 | 退回纯 AntD 5 `Table` / `Form` / `Descriptions` | 页面重写约半天；API 心智一致，逻辑不变 |
| openapi-typescript | 生成的类型与手写代码冲突过多 | 保留手写 interface，删掉 `gen:api` 脚本 | 回到 v1.0 状态，风险已知 |
| pgvector 镜像 | 拉取失败 / 团队环境不允许 | 改回 `postgres:16-alpine` | `pg_trgm` 两个镜像都有，**功能零损失** |
| `pg_trgm` | 迁移失败 | 退回 `ILIKE` | 数据量小时性能可接受 |
| Faker | 无（纯 dev 依赖） | 删掉即可 | 无 |
| Trafilatura 回退链 | 抽不到正文的源太多 | 全部退化为"只用 RSS 摘要"，`full_text_status` 恒为 `blocked` | 事实锚点质量下降，但流程不断 |
| tenacity 重试 | 无（失败率实测必须要有） | 不可回退——去掉即约半数请求失败 | — |
