我看完了这份《“神秘新闻”新闻采集与推送需求文档 v1.0》。

先说我的判断：**这不是一个单纯的新闻爬虫项目，而是一个结合新闻采集、内容筛选、AI 新闻加工、真实性校验、人工审核和新闻推送的自动化内容运营系统。**

它真正要解决的问题是：每天从大量新闻来源中，自动找出符合“神秘新闻”栏目定位的事件，把它们加工成适合娱乐 App 展示的标题和正文，再通过审核流程推送出去。

下面我从产品目标、功能模块、处理流程、技术实现和开发难点几个方面拆开讲。

# **一、先理解这个项目到底要做什么**

## **1. 产品定位**

这个 App 有一个叫“神秘新闻”的新闻栏目，主要关注五类内容：

| 内容类型          | 具体内容                           |
| ----------------- | ---------------------------------- |
| 深空 / 粒子       | 中微子、暗物质、引力波、粒子实验等 |
| 近地天体          | 小行星接近地球、近地天体发现等     |
| 新星球 / 类地行星 | 系外行星、宜居带行星等             |
| 脑机 / 意识技术   | 脑电控制机械臂、意念控制实验等     |
| 异常 / 灵能符号   | UFO、UAP、灵异综艺、通灵、术数等   |

注意，它不是要做一个普通的科技新闻网站。

比如，同一条新闻：

- 普通科技新闻标题：江门中微子实验取得阶段性成果。
- 神秘新闻标题：科学家抓到“鬼”了？

然后用户点进去，正文马上解释：

> 别怕，这里的“鬼”是几乎不跟物质反应的中微子，也叫“幽灵粒子”。中国江门中微子实验这次测到了关键数据。

这就是整个产品的核心思路：

**标题负责吸引用户，正文负责还原事实。**

标题允许娱乐化，但是不能歪曲事实。

## **2. 它不是什么内容都收集**

这个地方很重要，因为它决定了后面的筛选逻辑。

例如：

| 新闻内容               | 是否收录 | 原因                   |
| ---------------------- | -------- | ---------------------- |
| 江门中微子实验发布成果 | 收录     | 有具体科研事件         |
| 中微子是什么？一文读懂 | 拒绝     | 纯科普                 |
| 某小行星即将飞掠地球   | 收录     | 有具体时间节点         |
| 普通星空摄影图片       | 拒绝     | 没有事件               |
| 脑电控制机械臂实验     | 收录     | 有实际技术突破         |
| 脑机接口头环预售       | 拒绝     | 商业广告               |
| UFO 无来源视频         | 待定     | 缺乏可靠信源           |
| 泰国灵异综艺道士参赛   | 待定     | 娱乐事件，需要谨慎处理 |

所以，这个系统的第一项重要能力就是：**判断一条新闻是不是符合栏目定位的真实事件。**

# **二、把整个项目拆成六个功能模块**

我建议你把项目理解为下面六个模块，而不是一开始就把它当成一个大系统来做。

## **新闻采集与推送系统**

**① 新闻采集模块**

RSS / Google News / 聚合 API / 新闻源

**② 新闻预处理与筛选模块**

清洗 / 来源分级 / 关键词过滤 / 事件分类 / 真实性判断

**③ 去重与时效判断模块**

跨来源去重 / 新闻时间提取 / 24—48 小时有效期

**④ AI 内容加工模块**

标题生成 / 正文生成 / 事实锚点 / 风险检测 / 评分

**⑤ 候选 / 推送池**

低风险内容

**待定 / 人工审核池**

高风险内容

**⑥ 新闻推送模块**

审核通过 / 发布 / 状态记录 / 来源留存

接下来逐个分析。

## **模块一：新闻采集**

数据入口

**目标：从互联网的不同信息源，持续获取可能符合栏目定位的新闻。**

需求文档列举了几种采集方式：

| 来源               | 作用                           |
| ------------------ | ------------------------------ |
| NASA / ESA         | 太空、天体相关事件             |
| Fermilab           | 粒子物理等科研新闻             |
| ATel               | 天文观测事件信息               |
| ScienceDaily       | 科学研究、脑机接口等新闻       |
| phys.org           | 科研新闻                       |
| Google News RSS    | 根据关键词发现新闻             |
| 聚合 API           | 扩大新闻采集范围               |
| 微博、论坛、自媒体 | 发现线索，不能直接作为推送依据 |

文档还规定了不同来源的轮询频率：

- ATel、NASA、ScienceDaily BCI 等：15—30 分钟。
- Google News：1—2 小时。
- 聚合 API：根据套餐额度配置。

### **这里实际要开发什么？**

我认为可以拆成三个子功能：

**1. 信源管理**

管理系统要从哪些网站或 API 获取信息。

例如：

```
source_id
source_name
source_type
source_url
source_level
poll_interval
enabled
last_crawl_time
```

**2. 采集任务**

周期性运行采集任务，根据不同来源的接口获取新闻。

例如：

```
NASA RSS       每 20 分钟执行
Google News    每 1 小时执行
ScienceDaily   每 30 分钟执行
```

可以使用定时任务调度器，而不是自己写一个永久运行的死循环。

**3. 新闻标准化**

不同网站返回的数据格式不一样。

可能有的 RSS 返回：

```
{
  "title": "New asteroid discovered",
  "link": "https://example.com/news/123",
  "published": "2026-11-25T08:00:00Z",
  "description": "..."
}
```

另一个 API 返回的字段可能完全不同。

因此需要把它们统一转换成系统内部的新闻对象：

```
{
  "title": "New asteroid discovered",
  "url": "https://example.com/news/123",
  "summary": "...",
  "source_name": "NASA",
  "source_level": "A",
  "publish_time": "...",
  "crawl_time": "..."
}
```

**这个模块的关键不是爬虫技术有多复杂，而是如何接入不同信息源，并统一处理数据。**

## **模块二：新闻过滤与事件判断**

核心业务逻辑

这一部分是整个项目非常重要的环节。

采集到的新闻数量可能很多，但并不是所有新闻都符合要求。

例如，采集到以下几条：

```
A. 科学家发现一颗新的类地行星
B. 什么是系外行星？一文了解
C. 科学家利用脑电信号控制机械臂
D. 脑机接口头环产品即将上市
```

系统需要判断：

```
A -> 保留
B -> 拒绝
C -> 保留
D -> 拒绝
```

文档实际上规定了三层判断。

### **第一层：关键词规则过滤**

先用规则排除一些明显不符合要求的内容。

例如：

```
教程
攻略
手把手
星座运势
预售
广告
小说
影视科幻
普通美图
```

这部分不需要调用大模型，可以使用普通字符串匹配、正则表达式或规则配置。

### **第二层：事件分类**

判断新闻属于哪一类：

```
deep_space       深空/粒子
near_earth       近地天体
exoplanet        新星球
brain_computer   脑机/意识
paranormal       异常/灵能
```

可以使用关键词匹配作为初筛，再用大模型辅助判断。

### **第三层：事件型判断 is_event**

文档专门设计了一个字段：

```
{
  "is_event": true
}
```

这个字段代表新闻是否描述了一个刚发生或刚宣布的具体事件。

例如：

- “中微子是什么？”：false。
- “江门中微子实验公布首个成果”：true。

这里就比较适合使用大模型进行分类。

可以要求模型输出结构化 JSON：

```
{
  "is_event": true,
  "event_type": "deep_space",
  "reason": "新闻描述了具体科研成果发布事件"
}
```

但要注意，大模型判断的是内容类型和事件属性，不应该直接承担事实真实性的最终证明。

### **第四层：信源真实性判断**

文档将信源分为 A、B、C 三个等级：

| 等级 | 处理方式                                                     |
| ---- | ------------------------------------------------------------ |
| A 级 | NASA、ESA、Fermilab 等可靠来源，可以进入候选池               |
| B 级 | 聚合 API、Google News 等，需要回溯原始新闻链接               |
| C 级 | 微博、论坛、自媒体等，只能作为线索，必须人工复核或等待可靠来源确认 |

比如，微博上有人发布 UFO 视频。

系统不能直接把它加工成：

> 外星人终于被证实存在！

而应该把它放入待定池，等待其他可靠来源验证。

**我认为这里最需要注意的是：AI 分类、信源可信度和事实真实性是三个不同的问题。**

不能因为某个新闻来自大网站，就认为它一定符合栏目要求；也不能因为大模型判断它是一个新闻事件，就认为事件已经被证实。

## **模块三：时效判断与新闻去重**

数据质量控制

这一部分看上去比较简单，但实际开发时会碰到一些问题。

### **1. 时效判断**

每条新闻需要记录四个时间：

```
publish_time    发布时间
crawl_time      抓取时间
event_time      事件发生时间
first_seen_time 首次发现时间
```

为什么要记录这么多？

假设今天是 11 月 25 日：

某新闻在 11 月 20 日发生，但媒体在 11 月 24 日才发布报道。

那么：

```
event_time   = 11 月 20 日
publish_time = 11 月 24 日
crawl_time   = 11 月 25 日
```

单纯看抓取时间，就会误以为它是一条刚刚发生的新闻。

所以需要结合事件发生时间和发布时间判断是否具有推送价值。

文档规定推送新闻要在 24—48 小时内，后面的推送条件又明确要求 48 小时内。

### **2. 新闻去重**

这是我认为比较值得认真设计的地方。

例如，某小行星接近地球的新闻：

```
NASA：某小行星即将飞掠地球
ScienceDaily：新发现的小行星接近地球
某新闻网站：小行星将在本周擦肩地球
Google News：小行星近距离飞掠地球
```

它们实际上可能描述的是同一件事。

如果只是按照 URL 去重，是没有效果的，因为它们是不同网址。

文档要求使用：

- 标题规范化指纹。
- 关键实体跨来源去重。

我建议可以把去重分成两层：

**第一层：简单去重**

把标题进行标准化：

```
小行星即将飞掠地球！
小行星即将飞掠地球
小行星 将 飞掠 地球
```

去掉标点、空格等，再生成 Hash。

**第二层：语义去重**

利用实体和事件信息识别是否是同一事件。

例如：

```
{
  "event_type": "near_earth",
  "entity": "Asteroid 2026 XX",
  "event_action": "flyby",
  "event_date": "2026-11-26"
}
```

当不同来源的新闻对应相同天体、事件类型和时间时，就可以判断它们可能是同一事件。

不一定一开始就上向量数据库。对于这个项目，规则、实体匹配以及必要时的大模型辅助判断，已经可以构成比较合理的初版。

## **模块四：AI 新闻标题和正文生成**

AI 核心功能

这部分是项目中最明显需要调用大模型的地方。

系统拿到一条合格的新闻后，需要生成适合 App 展示的内容。

文档要求生成四类重要内容。

| 字段             | 用途       | 要求                       |
| ---------------- | ---------- | -------------------------- |
| title_candidates | 标题候选   | 生成 3—5 个                |
| title_final      | 最终标题   | 10—18 字，只保留悬念钩子   |
| body_lead        | 正文第一段 | 20—60 字，马上解释标题悬念 |
| body_summary     | 正文摘要   | 80—120 字，大白话说明事件  |

### **1. 标题生成**

比如原始新闻：

```
科学家使用脑电信号控制机械臂完成动作
```

大模型生成：

```
{
  "title_candidates": [
    "不用手也能驭剑？",
    "意念控制真的来了？",
    "人类开始用脑子操控机器了？"
  ]
}
```

系统再根据标题的吸引力、事实准确性和风险情况选择最终标题。

### **2. 正文生成**

正文不能跟着标题一起玩悬疑。

例如最终标题：

> 不用手也能驭剑？

正文第一段应该解释：

> 这是脑电信号控制机械臂的实验，并不是真正的意念驭剑。受试者通过脑电信号控制设备完成了相应动作。

后面再补充事件背景、实验主体、成果和意义。

### **3. 事实锚点 fact_anchor**

这个字段我觉得特别值得关注。

文档要求每个标题都保存一个事实锚点，供审核人员检查。

例如：

```
{
  "title_final": "不用手也能驭剑？",
  "fact_anchor": "实验人员利用脑电信号控制机械臂完成指定动作",
  "body_lead": "这是脑电控制机械臂的实验，并非真正的意念控制物体。"
}
```

为什么要有它？

因为模型可能会为了标题吸引力而夸大事实。

比如原新闻只是实验室环境下控制机械臂，标题却变成：

> 人类已经掌握意念控制！

这就不符合要求。

因此，`fact_anchor` 相当于标题和正文对应的事实依据，方便后续审核。

### **4. 标题风险检测**

文档还定义了：

```
hook_score   抓眼球分数，1—5
risk_flags   风险标记
style_tag    标题风格
```

例如：

```
{
  "hook_score": 5,
  "style_tag": "科幻片式",
  "risk_flags": [
    "绝对化表达",
    "标题正文不一致"
  ]
}
```

这一步可以让模型进行初步检查，也可以加一些确定性的规则：

- 是否有“已确认外星人”等没有事实依据的绝对化词语？
- 是否把实验描述为已经实现大规模应用？
- 标题是否超出规定字数？
- 正文有没有解释标题的悬念？
- 是否出现标题和正文事实不一致？

但要明确，AI 风险检测不等于事实核查。高风险内容仍然需要人工审核。

## **模块五：候选池、待定池与人工审核后台**

业务管理模块

这个模块容易被忽略，但需求文档其实非常强调它。

系统不是：

```
爬到新闻 -> AI 改写 -> 直接推送
```

而是：

```
爬到新闻
   |
   v
自动筛选和加工
   |
   +---- 低风险内容 -> 候选/推送池
   |
   +---- 高风险内容 -> 待定池
                            |
                            v
                         人工审核
                            |
                    +-------+-------+
                    |               |
                  通过             拒绝
                    |               |
                    v               v
                  推送           记录原因
```

为什么要有两个池？

因为有些新闻可能是真的，但是存在一定风险。

例如：

- 新闻来源不确定。
- UFO 内容缺乏足够证据。
- 灵异综艺容易被描述成真实超自然现象。
- 标题有明显夸大。
- 事实依据不足。

这些新闻不应该直接被自动推送。

### **后台应该做什么？**

至少需要以下几个页面或功能：

| 功能     | 作用                               |
| -------- | ---------------------------------- |
| 新闻列表 | 查看所有采集到的新闻               |
| 候选池   | 查看符合基本条件的新闻             |
| 待定池   | 查看需要进一步确认的新闻           |
| 新闻详情 | 查看原始新闻、来源、生成标题和正文 |
| 审核操作 | 通过、拒绝、修改内容               |
| 状态管理 | 候选、待定、通过、拒绝、已推送     |
| 拒绝原因 | 保存为什么这条新闻不能推送         |

这里建议一定要能够看到原始来源和原始内容，否则审核人员很难判断 AI 生成的内容有没有歪曲事实。

文档也明确要求保留来源链接和来源等级，并且先建设候选池、待定池和人工审核后台，不做爬虫直通用户。

## **模块六：新闻推送**

最后一步就是将审核通过的新闻推送到 App。

但这里有一个需要注意的地方：

**需求文档只定义了新闻推送的业务条件，没有详细规定 App 端推送接口。**

因此，实际开发前需要确认：

- 是调用已有 App 后端 API，还是只需要提供新闻管理后台？
- 推送到 App 的新闻栏目，还是通过消息通知推送？
- 是否需要定时发布？
- 是否需要编辑人员最后确认？
- 推送失败后是否需要自动重试？

在没有这些信息的情况下，我不会把某一种具体推送方案当成已经确定的需求。

# **三、把需求转换成实际开发任务**

如果我们从软件工程的角度来做，可以分成下面这些任务。

| 阶段        | 具体开发任务                           | 主要产出     |
| ----------- | -------------------------------------- | ------------ |
| 1. 基础设施 | 数据库、后端服务、管理后台基础框架     | 可运行的系统 |
| 2. 新闻采集 | RSS、API 接入，定时采集，数据标准化    | 原始新闻库   |
| 3. 新闻过滤 | 关键词过滤、来源等级、事件分类         | 新闻候选数据 |
| 4. 新闻去重 | 标题指纹、实体匹配、跨源去重           | 去重后的新闻 |
| 5. AI 加工  | 事件判断、标题生成、正文生成、风险评分 | AI 加工结果  |
| 6. 审核后台 | 候选池、待定池、人工审核、状态管理     | 内容审核系统 |
| 7. 新闻推送 | 审核通过、发布接口、推送记录           | 新闻发布链路 |

我建议不要一开始就做完整的 AI 自动化系统。可以按下面的顺序迭代。

# **四、推荐的实际开发顺序**

1. **第一阶段：先打通新闻采集**

   先接入 2—3 个 RSS 源，完成定时采集、数据解析和入库。

   验收：系统可以持续采集新闻，并且每条新闻都能追溯原始链接。

2. **第二阶段：完成基础筛选和去重**

   做关键词过滤、来源等级、事件分类、时间判断和标题指纹去重。

   验收：明显的科普、广告、星座运势等可以被过滤，重复新闻不会反复进入候选池。

3. **第三阶段：接入大模型**

   先做 `is_event` 分类，再做标题和正文生成，最后增加风险检测。

   验收：能够对符合条件的新闻生成规定格式的标题和正文，并保留事实锚点。

4. **第四阶段：实现审核后台**

   展示新闻原文、来源、AI 生成结果、评分和风险标记，支持审核通过、拒绝和修改。

   验收：可以完整管理一条新闻从候选到通过或拒绝的状态变化。

5. **第五阶段：打通推送流程**

   接入实际 App 发布接口，处理推送成功、失败和重复发布。

   验收：只有符合推送条件的审核通过新闻才能发布。

# **五、从技术角度看，哪些地方比较有难度？**

我把难点按实际开发的重要性排了一下。

| 难点              | 难度判断 | 原因                                   |
| ----------------- | -------- | -------------------------------------- |
| RSS / API 采集    | 中等     | 不同来源格式不同，接口稳定性和额度有限 |
| 事件筛选          | 中等     | 需要兼顾召回率和准确率                 |
| 跨来源去重        | 中高     | 同一事件可能有不同标题和描述           |
| 事实真实性验证    | 高       | AI 无法仅凭新闻文本证明事件真实        |
| AI 标题与正文生成 | 中等     | Prompt、结构化输出和事实约束           |
| 风险识别          | 中高     | 标题可能夸大，灵异内容尤其容易越界     |
| 审核后台          | 中等     | 业务状态和人工操作流程                 |
| 定时任务和稳定性  | 中等     | 重试、并发、重复执行、任务失败恢复     |

我想特别强调三个问题。

**第一，新闻采集不等于新闻真实性验证。**

一个网站提供了新闻，并不代表内容一定真实。系统需要保留原始链接、来源等级以及核验依据。

**第二，去重比想象中复杂。**

同一个事件可能在不同媒体上使用完全不同的标题。只用 URL 或标题 Hash，无法很好地解决跨来源重复问题。

**第三，AI 最容易出问题的地方是为了吸引眼球而夸大事实。**

因此，AI 生成内容时需要约束事实来源，并且把自动筛选和人工审核结合起来。

# **七、我对这个题目的整体评价**

我认为这个项目的核心其实不是爬虫，也不是大模型，而是一个**AI 辅助的新闻内容生产流水线**。

它的技术结构可以概括为：

**数据采集层**

RSS、第三方 API、新闻源

**业务处理层**

清洗、筛选、分类、去重、时效判断

**AI 服务层**

事件识别、标题生成、正文生成、风险检测

**业务管理层**

候选池、待定池、人工审核、状态流转

**发布层**

App 新闻接口、推送记录、失败处理

从开发工作量来看，它不是一个单纯写几个接口就能完成的小项目，但也没有必要一开始就引入复杂的微服务、消息队列和分布式架构。

初版可以用一个后端服务、关系型数据库、定时任务、AI API 和一个管理后台完成。等采集源和新闻量增加之后，再根据实际瓶颈考虑消息队列、任务调度和服务拆分。

**我觉得你接下来最应该搞清楚的是：这道实习题究竟要求你交付什么。**

因为它有两个完全不同的完成标准：

1. **功能型交付**：做一个能采集新闻、AI 改写、人工审核、推送的完整系统。
2. **原型型交付**：接几个新闻源，跑通采集到 AI 生成的流程，用简单后台展示结果，证明核心链路可行。

两者的工作量差距很大。就这份需求文档而言，我更倾向于它描述的是一个可持续运行的业务系统，而不是单纯的 AI Demo；但文档没有给出明确的交付范围和验收环境，所以还不能确定实习题要求做到哪一层。

**我的建议是先把它当成一个内容流水线项目，优先打通“采集 → 筛选 → AI 加工 → 人工审核”这条主链路，推送接口等拿到具体要求后再实现。**
