# 后台多账号与「切换账号」接口需求

> 提出方：前端 / 运营侧　接收方：后端　状态：待评估　日期：2026-11-27
> 本文只描述接口需求与验收标准，**不含任何后端代码改动**。前端界面已按最终形态实现，接口就绪后可直接对接。

## 1. 背景

后台目前是**单管理员**模型：账号来源是环境变量，没有用户表，也没有「切换账号」的能力。

| 项 | 现状 |
|---|---|
| 账号来源 | `.env` 的 `ADMIN_USERNAME` + `ADMIN_PASSWORD_HASH`（bcrypt） |
| 用户表 | 无（`backend/app/models/` 下没有 users/accounts 模型） |
| 认证方式 | JWT 存 HttpOnly Cookie，字段 `sub=username`，实现见 `backend/app/api/auth.py` 与 `app/api/deps.py`（`COOKIE_NAME = "mn_token"`、`JWT_ALGORITHM = "HS256"`） |
| 现有接口 | 仅 3 个：`POST /api/auth/login`、`POST /api/auth/logout`、`GET /api/auth/me` |
| 权限模型 | 无角色概念，登录即拥有全部后台能力 |
| 审计 | 有 `review_action` 等审计写入 helper，登录/审核等动作可落库 |

运营侧的实际问题是：多个运营同学共用同一个 `admin` 账号，审核记录无法区分「是谁审的」，出了问题无法追溯；同时切换身份必须退出再登录，体验差。

## 2. 目标与非目标

**目标**

1. 支持多个后台账号（至少 2 个以上），账号有稳定的主键、显示名与角色。
2. 已登录状态下可以**不退出登录**直接切换到另一个有权限的账号。
3. 所有写操作与审核动作能记录「实际执行人」，可追溯。
4. 兼容现状：老部署只配了 `ADMIN_USERNAME` / `ADMIN_PASSWORD_HASH` 也能平滑升级，不需要人工改数据。

**本期不做**

- 第三方登录（OAuth / SSO / 企业微信）。
- 细粒度到按钮级的权限点体系（本期只要角色枚举 + 接口级校验即可）。
- 账号自助注册、找回密码邮件流（由管理员在后台重置密码即可）。

## 3. 期望接口（契约草案，字段名可协商）

统一约定：沿用现有封装，鉴权依赖 `mn_token` Cookie；错误体沿用现有统一错误结构；时间统一 UTC ISO8601。

### 3.1 `GET /api/auth/accounts` — 可切换账号列表

需要登录。返回当前登录者**有权切换过去**的账号（不含密码、哈希、令牌等敏感字段）。

```json
{
  "items": [
    {
      "id": 1,
      "username": "admin",
      "display_name": "主管理员",
      "role": "owner",
      "is_current": true,
      "is_active": true,
      "last_login_at": "2026-11-27T09:12:03Z"
    },
    {
      "id": 2,
      "username": "reviewer01",
      "display_name": "审核-小王",
      "role": "reviewer",
      "is_current": false,
      "is_active": true,
      "last_login_at": "2026-11-26T14:02:11Z"
    }
  ]
}
```

- 若一期只允许「单管理员 + 若干只读账号」这种简化策略，也请返回真实列表，前端按 `is_active` 与 `role` 渲染。
- 前端弹层里的账号区目前只展示当前账号；列表返回后即可渲染成可点选的账号列表。

### 3.2 `POST /api/auth/switch` — 切换账号

需要登录。请求体二选一（推荐用 `account_id`，避免用户名变更导致的问题）：

```json
{ "account_id": 2 }
```

行为要求：

1. 校验当前会话有效（当前 `mn_token` 可用）。
2. 校验目标账号存在且 `is_active = true`。
3. 校验当前登录者**有权**切换到该账号；无权限返回 `403`。
4. 签发新的 JWT（`sub` 为被切换账号的标识，建议用 `user_id` 而非 username），**覆盖写**同名 Cookie `mn_token`（HttpOnly / SameSite / Path 与登录接口保持一致，`max_age` 沿用 `JWT_EXPIRE_MINUTES`）。
5. 写审计：记录「谁在什么时间切换到了谁」（可复用现有审计 helper）。
6. 返回与 `/api/auth/me` 同构的对象，便于前端直接刷新页面头部信息。

```json
{ "ok": true, "username": "reviewer01", "display_name": "审核-小王", "role": "reviewer" }
```

错误约定：`401` 未登录、`403` 无权切换、`404` 目标账号不存在、`409` 目标账号已停用。

### 3.3 `GET /api/auth/me` — 扩展字段（向后兼容）

前端现在只读 `username`，请**保留该字段**，并补充：

```json
{ "ok": true, "username": "admin", "id": 1, "display_name": "主管理员", "role": "owner" }
```

### 3.4 （可选）账号管理接口

若本期一并做，建议：

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/admin/accounts` | 账号列表（含停用账号，仅 `owner` 可见） |
| `POST` | `/api/admin/accounts` | 新建账号（username / password / display_name / role） |
| `PATCH` | `/api/admin/accounts/{id}` | 改显示名、角色、启停、重置密码 |
| `DELETE` | `/api/admin/accounts/{id}` | 停用（建议软删，保留审计关联） |

权限：仅 `owner` 可调用；不允许删除/停用自己；不允许把最后一个 `owner` 降级。

## 4. 数据模型建议

新增表（建议迁移文件名 `0008_users.py`）：

```text
users
  id            serial PK
  username      varchar(64) unique not null
  password_hash varchar(255) not null        -- bcrypt，复用现有 --hash-password 逻辑
  display_name  varchar(64)
  role          varchar(16) not null         -- owner / admin / reviewer
  is_active     boolean not null default true
  last_login_at timestamptz null
  created_at    timestamptz not null default now()
  updated_at    timestamptz not null default now()
```

补充建议：

- JWT 的 `sub` 从 `username` 改为 `id`（或新增 `uid` claim），避免改用户名后历史 token 语义错乱；`deps.current_admin` 需要相应解析并回落到用户名以兼容旧 token。
- 如需「切换后旧会话失效」，可加 `token_version int`（用户表）并在 JWT 里带版本号，切换时自增即可，不必引入 Redis/会话表（仓库红线：只允许一个 db 容器）。

## 5. 兼容与迁移

1. Alembic 迁移后，启动时若 `users` 表为空，则用 `ADMIN_USERNAME` + `ADMIN_PASSWORD_HASH` 播种一条 `role = owner` 的记录。
2. `ADMIN_USERNAME` / `ADMIN_PASSWORD_HASH` **保留**作为初始播种来源（不要让已有部署升级即不可登录）。
3. 登录接口改为查表校验密码；表内无匹配时回落到环境变量比对，保证平滑过渡，并在日志里提示「仍在用环境变量登录，建议迁入 users 表」。
4. 所有依赖 `current_admin`（返回 username 字符串）的接口保持不变；内部实现改为能取到 user 记录。

## 7. 验收标准

1. 只配 `ADMIN_USERNAME`/`ADMIN_PASSWORD_HASH` 的老部署，执行迁移并重启后可以正常登录（不报错、不需要手工插数据）。
2. `GET /api/auth/accounts` 返回的 `is_current` 与当前 `mn_token` 一致，且**不包含**任何密码/哈希/令牌字段。
3. `POST /api/auth/switch` 成功后，浏览器 `mn_token` 被替换，紧接着调用 `/api/auth/me` 返回新账号；刷新页面侧栏显示新账号名。
4. 无权限切换的目标账号返回 `403` 且当前会话不被破坏；停用账号返回 `409`。
5. 切换动作在审计中留有记录（谁 → 谁、时间、来源 IP 可选）。
6. 切换后执行一次审核发布，审计的执行人是新账号，而非原账号。
7. 迁移可回滚（`alembic downgrade -1` 不破坏既有业务表）。

3. 切换是否需要二次验证（例如再次输入目标账号密码）？前端可以配合加一栏密码输入。

5. 审计里是否需要记录切换来源 IP / User-Agent（当前审计表是否已有可用字段）。
